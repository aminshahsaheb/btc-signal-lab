# D-LIQ G-1 dry run — format-only capture tool (DRAFT)

STATUS: **DRAFT. Not independently reviewed. Run by the owner against the real exchange on 2026-11-09 (three runs) and on 2026-11-10 (run 9, one BTCUSDT frame); see "What the real runs showed"; format observations only.** Nothing here is a result, a collector, a probe, T0 or an edge claim. The raw captures stay with the owner, outside Git, unless the owner explicitly approves committing them. The tests below run against a fake local server written by the same author as the tool; they show that the code follows the websocket protocol as the author understood it, not that the exchange behaves that way: only the real runs show that, and they covered 26 frames from one machine and one VPN.

## Why it exists
Every field name and stream shape in the G-1 CANDLE proposal and in the message contract is `[VERIFY]` (documentation or third-party clients only), and the endpoint path of the single-symbol `forceOrder` stream is unverified (ROADMAP 2F, OPEN-10 / OPEN-13). The collector host is undecided and the owner's own connection to the exchange is not available directly. This tool lets the owner look at the real wire format once, for free, from his own computer through a VPN, before any server is paid for. It records **at most 20 raw `forceOrder` frames and at most 10 `kline_1m` frames** of BTCUSDT and nothing else (hard limits in the code, enforced and tested).

## What it does and does not do
- Connects only to `fstream.binance.com:443` over TLS (certificate and host name are verified; there is no switch to turn that off). Public market-data streams only. No login, no API key, no order, no account, no cookie, no upload, no environment-variable access.
- Writes only into a NEW directory that must not exist yet, using exclusive-create file modes: `capture.jsonl` (one line per recorded frame: exact bytes as base64, SHA-256, local receive time in ms, connection label, route path) and `summary.json` (outcome of each connection, HTTP status and `Date` header of the handshake, counters, Python and platform string). It contains no IP address and no personal data.
- Does no price, outcome, liquidation-size or "edge" analysis. It only classifies a frame as `force` / `kline` / `other` to count and cap it; the raw bytes are what is stored.
- Stops by itself: hard caps on frames, on seconds per connection (default 600, maximum 1800), and a stop after the first connection only if that connection could not be OPENED at all (a connection that opened and was hung up later does not stop the run: version 3). A connection that gets **no answer at all** from the network (dead VPN tunnel: TCP/TLS/HTTP timeout) is tried up to 3 times (`--connect-attempts`, hard limit 5, 5 s apart, `--connect-timeout` 5-60 s per try); a real refusal (HTTP 451/403), a certificate error or anything after the handshake is never retried. A failed try records nothing.
- Standard library only (Python 3.8+). Needs the flag `--i-approve-format-only-dryrun`; without it the tool prints the plan and exits without doing anything. Passing the flag is the owner's explicit approval that ROADMAP 2F requires, for exactly the capture printed in the plan.

## Plan it executes (default route `market`)
| # | label | path | records |
|---|---|---|---|
| 1 | `kline_raw` | `/market/ws/btcusdt@kline_1m` | up to 3 kline frames (60 s) |
| 2 | `combined` | `/market/stream?streams=btcusdt@forceOrder/btcusdt@kline_1m` | up to 6 kline and 10 forceOrder frames |
| 3 | `force_raw` | `/market/ws/btcusdt@forceOrder` | up to the remaining forceOrder budget (20 in total) |
**Watch mode** (version 4; GPT requires one genuine BTCUSDT `forceOrder` frame before any lock): `--watch-btc-minutes M` (1-120) keeps ONLY `/market/ws/btcusdt@forceOrder` open and reconnects 3 s after every hang-up (a VPN that cuts connections every ~50 s is the reason), until `--watch-stop-after N` frames (default 1, never more than `--max-force`) arrived, the time is over, 300 connections were made, or 3 rounds in a row could not open a connection at all. It cannot be combined with the other options below. On a Mac put `caffeinate -i` in front of the command so the computer does not sleep. A quiet 51-53 s connection is not evidence of a broken route.
Optional: `--skip-kline-raw` (drop row 1, e.g. when kline frames are already captured), `--also-all-market` (all-symbol liquidation stream, same message format, for when BTCUSDT is quiet), `--also-legacy` (the old unrouted `/ws/btcusdt@forceOrder` path for 60 s, diagnostic), `--route public` / `--route none` (other route prefixes if `/market` is refused).

## What the real runs showed (owner's computer, VPN; 2026-11-09 22:24Z to 23:12Z, tool versions 1 and 3, and 2026-11-10 19:35Z to 19:40Z, tool version 4; frames NOT committed)
Seven connections reached the exchange (HTTP 101) and delivered 26 frames in all: 18 kline (6 RAW, 12 COMBINED) and 8 `forceOrder` (all-market stream); two further connections (single-symbol `forceOrder`) were accepted and delivered nothing. Observed, not generalised:
- **Routing.** The routed paths accepted the connection: `/market/ws/btcusdt@kline_1m`, `/market/stream?streams=btcusdt@forceOrder/btcusdt@kline_1m`, `/market/ws/btcusdt@forceOrder` (HTTP 101 twice, but NO frame in 51-53 s each time; BTCUSDT liquidations are rare) and `/market/ws/!forceOrder@arr` (8 frames). The legacy unrouted path and `/public` were not tried. The TLS chain was a normal DigiCert chain (so the VPN does not intercept TLS); responses carried a `Date` header and no `Server` header.
- **kline.** RAW: outer keys `e, E, s, k`; COMBINED: exactly `{"stream": "btcusdt@kline_1m", "data": {...}}`. Keys of `k`: `t, T, s, i, f, L, o, c, h, l, v, n, x, q, V, Q, B`; `k.t` a multiple of 60000, `k.T = k.t + 59999`, `k.o` a decimal string, `k.x` a boolean. Irregular whitespace (", " inside `k`, none outside): store raw bytes, never re-serialise. The G-1 parser `parse_kline_frame` accepted all 18 kline frames unchanged. One COMBINED frame was the closing message of a minute (`x = true`, `E` = `T` + 596 ms): the "closing message arrives after T" case that G-1 section 3.3 describes as normal. Spacing between consecutive updates in the samples was 260-877 ms (not a fixed 250 ms).
- **forceOrder (all-market stream only, 8 frames, all `X = FILLED`, all `S = SELL`, `o = LIMIT`, `f = IOC`).** Unwrapped RAW message, outer keys exactly `e, E, o`; `o` holds the eleven fields of the message contract (`s, S, o, f, q, p, ap, X, l, z, T`) **plus two more, `ps` and `st`, INSIDE `o`** (`ps` equal to `s`, `st` = 1 in all 8). The official page (small-model summary, `[VERIFY]`) lists `ps` and `st` at the top level, as all-market-only fields (`st`: 1 = UM, 2 = CM) and says the single-symbol stream does not have them; on the wire they are inside `o`. The contract's `classify()` ignores unknown keys inside `o`, so it is not broken by them, but its `st` rule reads `msg["st"]` at the TOP level and therefore never fires on real data: **[DECISION for GPT]** drop that rule or move it to `o.st` (it concerns a stream the study does not use, if the page is right). `E` is about 1.0 s after `T` (1002-1006 ms in all 8), consistent with the 1000 ms per-symbol snapshot; frames of different symbols sometimes share one `E`. With the symbol relabelled to BTCUSDT in a COPY (synthetic, only to exercise the grammar), the contract's `classify()` returned ELIGIBLE for all 8; with the real symbols it returns MALFORMED/`symbol`, as designed.
- **A genuine BTCUSDT `forceOrder` frame was captured on 2026-11-10 (run 9, tool version 4, watch mode; 19:35Z to 19:40Z, same macOS machine and VPN; frame NOT committed).** Five connections to `/market/ws/btcusdt@forceOrder` (HTTP 101 each); the first four were cut by the peer after 53-55 s with no frame, the fifth delivered one frame after 30 s. ONE frame: 209 bytes, text, RAW (not wrapped), SHA-256 `537a499a9b1f10c62cf7f65c7d2a02f7d6038c0d56135bcad588fc92b32074ce` (the recorded hash matches the decoded bytes). Outer keys exactly `e, E, o`; `o` has the eleven contract fields AND `ps` (a string equal to `s` = `BTCUSDT`) AND `st` (the integer 1) INSIDE `o`, exactly as in the all-market frames; no top-level `st`. `X = FILLED`, `S = SELL`, `o = LIMIT`, `f = IOC`, `q = z`; `E - o.T` = 1005 ms (consistent with a per-symbol snapshot about 1 s after the order time). The unmodified `classify()` of the r5 contract code (same author as the tool) returns ELIGIBLE for it, because it ignores unknown keys inside `o` and its top-level `st` rule never fires. **This contradicts the assumption that the single-symbol stream carries no `ps`/`st`**; one frame is still one frame (no second frame, no other symbol, no variation of `X`, `S` or `st`), not a distribution. `recv_ms - E` was -942 ms (the laptop clock was behind by about 1 s, not 4.2 s as on 2026-11-09): laptop receipt times stay unusable for latency. No server ping was seen in 246 s of connections. No price or outcome analysis was done.
- **Clock.** `recv_ms - E` was between -4341 and -4168 ms in every frame: the owner's laptop clock is about 4.2-4.3 s behind the exchange (the HTTP `Date` header, 1 s resolution, agrees with `E`). Laptop receipt times say nothing about latency; the contract's 250 ms bound needs a real anchor on the collector host.
- **Hang-ups.** Four connections ended after 51-53 s and one after 103 s, all by a TCP close WITHOUT a WebSocket close frame (also the ones that were receiving data), so this looks like the VPN path, not the exchange (the documented lifetime is 24 h); it cannot be separated without a second network path. One server ping was seen in 103 s, which does not contradict a ping about every 3 minutes with an unknown phase.
- **Setup.** python.org Python on macOS needs "Install Certificates.command" once (otherwise `CERTIFICATE_VERIFY_FAILED ... self-signed certificate in certificate chain`). TLS handshakes through the owner's VPN (a TUN client with fake-IP DNS) timed out intermittently until a different node was chosen.

## Run (summary; the owner gets the exact steps in the conversation)
```
python3 dliq_format_dryrun.py --out-dir ~/dliq_dryrun_1                                  # prints the plan, does nothing
python3 dliq_format_dryrun.py --out-dir ~/dliq_dryrun_1 --i-approve-format-only-dryrun   # runs it
```
Tool version 2 added retries, `--connect-timeout` and `--skip-kline-raw`; version 3 stops only if the first connection could not be opened; the file hash to check is in the conversation, never trust a hash printed only in this README.
A system-wide VPN (not a browser-only extension) with an exit outside the USA must be on, because the Terminal does not use the browser's proxy. A run takes up to about 20 minutes (liquidations are bursty; zero `forceOrder` frames in 10 minutes is possible and is itself informative; then rerun with `--also-all-market`). On macOS with a python.org installation a `tls_certificate_error` usually means "Install Certificates.command" has not been run; do not work around it by disabling verification.

What to send back: `capture.jsonl` and `summary.json` of the run, the VPN exit country, and the local time. They are public market data. **They must not be committed to the repository** (ROADMAP rule: captured exchange frames need an owner decision first).

## What a good outcome would and would not mean
- It would settle: which routed path actually accepts the connection, whether `forceOrder` frames arrive on `/market/ws/btcusdt@forceOrder`, raw versus combined shape, the real field names for `E`, `o.*`, `k.t/T/o/x`, whether the legacy path still delivers data, and the HTTP status from the owner's VPN path.
- It would NOT settle: anything about latency, frame loss, 24 h stability, the 200 s health rule, `L` (decision B), a production host, a clock anchor, or any statistical property of liquidations. It is a handful of frames seen once from one network path.
